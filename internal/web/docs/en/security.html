Isolation and security

A hosting server runs other people's code, so HostZit treats every account as possibly compromised and keeps the accounts apart in several layers.

Isolation between accounts

  • Own Linux user per account; PHP-FPM runs as that user, never as root.
  • Own control group (cgroups v2) with the CPU, memory, IO and process limits of the package for PHP, cron, SSH and tools.
  • Private file system view: PHP, cron jobs, SSH and SFTP see only the account's own home, a private /tmp and a read-only system; other homes, other processes, the panel's files and the web server configuration are not there.
  • Disk quotas, separate database users, PHP open_basedir, programs from PHP off unless the package allows them.
  • The web server never follows a link to a file of another owner.
  • An isolation test suite (account A tries to read, list, write, signal and connect to account B) runs on real servers.

Mail from websites

Accounts cannot reach SMTP ports themselves (the firewall rejects outgoing SMTP for them). PHP's mail() puts messages into a queue, and HostZit sends them with the hourly limit of the package:

  • EmailZit on this server: through emailzit-sendmail for customers EmailZit knows (same customer); the websites of customers without mail in EmailZit stay with HostZit's own sending below.
  • EmailZit linked on another server: through EmailZit's relay login that came with the pairing (host, port and login from EmailZit, STARTTLS). HostZit signs the mail with the DKIM key of the domain (EmailZit signs only its own mail domains), and the default SPF record of the zones here also names EmailZit's mail host; EmailZit shows the mail to the customer.
  • An SMTP server for websites (Settings → Notifications, "Mail from websites goes through this SMTP server"), for example when the provider blocks port 25.
  • Otherwise HostZit delivers the mail itself: to the mail servers (MX) of the recipients on port 25, with STARTTLS when they offer it, signed with a DKIM key per domain (selector hz1). For zones on this server HostZit writes the DKIM record itself; for domains whose DNS is elsewhere the customer's Security page shows the TXT record to set. Settings → Notifications shows whether outgoing port 25 is open and whether the reverse DNS of the server's addresses is the server name; the overview warns when not.

The sender (From) must be an address on a domain of the account (its websites, aliases and zones); other messages are not sent. Bounces and replies go to the From address, so it should be one that receives mail (or the message should have a Reply-To). The Security page also shows what the SPF record of each domain needs. Customers see the queue and every sent, refused and failed message of the last 30 days under Security; undelivered mail is also a notice ("Website mail that could not be delivered"). Messages that cannot be delivered for 48 hours are dropped.

Whose domain is it?

Like in cPanel, customers can add any domain by default. With Customers must show that a domain is theirs (Settings → Sign-in and security) a customer adds a website, an alias or a DNS zone only when DNS shows that the domain is theirs: it already points at this server (A/AAAA record), its name servers are this server's name servers, or the TXT record _hostzit-verify.DOMAIN holds the value the panel shows (it stays the same for that customer and domain). Names below a zone the customer already has need no proof, and administrators (and the REST API) can always add a domain for a customer.

The panel

  • Root work only through hostzit-helper, with a fixed list of checked operations; configuration is written from templates, never from customer text.
  • Two-factor sign-in (required for administrators), roles, sign-in blocks after failed attempts, allowed networks for the admin panel, company sign-in (OpenID Connect).
  • Hash-chained audit log, secrets encrypted at rest, signed updates, four-eyes approval.

Encryption and network

  • Websites over HTTPS: TLS 1.3, and TLS 1.2 only with forward secrecy and AEAD ciphers (no CBC or SHA-1 ciphers).
  • Every HostZit server (the appliance and servers installed by script, since 0.9.5) offers SSH and SFTP only with strong algorithms: post-quantum key exchange (mlkem768, sntrup761) next to curve25519, Ed25519 and RSA host keys, AES-GCM/CTR, encrypt-then-MAC. On the appliance root cannot sign in over SSH.
  • LLMNR and multicast DNS (ports 5355 and 5353), meant for home networks, are switched off.
  • Incoming connections (Settings → Sign-in and security): only the ports HostZit uses accept connections from outside — SSH/SFTP (also a changed SSH port), DNS (53), the websites (80, 443), both panels and, with EmailZit on the server, its mail ports and panel. More ports can be opened there (TCP and UDP). Answers to the server's own connections, ping and DHCP always pass. New servers have it on from the setup; servers set up before 0.9.3 keep every port open until the administrator turns it on (the page warns).

Brute-force protection

An address that fails to sign in too often is blocked: in the panels (by the panel itself), for SSH and SFTP and for the sign-in of every WordPress website (both by fail2ban, which the panel sets up). The limits are the ones under Settings → Sign-in and security (failed sign-ins, counting period, block length; a repeated block doubles, up to 7 days). For WordPress a failure is a sign-in request over the limit of 10 a minute from one address.

Settings → Brute-force protection lists every blocked address with where it was blocked and until when, and lifts a block with Unblock. Under Never blocked enter your own addresses or networks (one per line, for example your office): they are never blocked; the server itself never is.

Access by country

Countries and continents can be refused, or only some allowed, in two places. Under Settings → Brute-force protection → Access by country the administrator sets who may reach the sign-in of the panels and SSH and SFTP (the server's firewall drops the rest; websites, mail and DNS stay open). Customers set a rule per website (Websites → the site → Access by country); visitors from refused countries get 403, certificate checks always pass. The same page lists every website with a country rule.

The country database is DB-IP's IP to Country Lite (free, CC BY 4.0): the administrator downloads it once with Download the country database (about 9 MB, the nginx module libnginx-mod-http-geoip2 is installed with it); it is updated every month by itself. Addresses of local networks and the addresses under Never blocked are never refused. Before a sign-in rule is saved the panel checks that your own address would still get in.

Malware scans

Administrators install ClamAV under Settings → Sign-in and security (it needs about 1 GB of memory while scanning) and may scan every account each night and move found files into the account's quarantine right away. Scans run at the lowest priority so the websites stay fast; a large account may take an hour or more (a scan stops after 6 hours). Customers scan under Security, administrators from the customer page. Found files are listed and reported by e-mail; Quarantine moves a file into ~/.quarantine without any permissions, outside every website, where it can be restored or deleted. Nothing is deleted automatically.

For WordPress, WordPress → the site → File check compares WordPress and its plugins from wordpress.org with the official checksums; changed or extra files are often a sign of a break-in. Replace the WordPress files downloads fresh copies of the same version (wp-content and wp-config.php stay).
